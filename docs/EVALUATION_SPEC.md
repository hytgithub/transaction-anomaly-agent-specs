# 智能体评测规范

- 项目：交易业务异常诊断 Agent
- 文档版本：0.1.0-draft
- 状态：草案，处于评测设计阶段
- 最近更新：2026-10-22

## 1. 目的

为 AgentScope 与 LangGraph 两个实现建立同一套、可重复、以数据和可验证结果为依据的评测方法。评测不仅检查最终根因是否正确，还要检查结论是否有真实证据支持、工具调用是否合理、是否遵守只读边界，以及运行结果是否可复现。

本规范定义评测设计与验收方法；当前不要求立即实现评分器，也不要求一次性构造大量案例。

## 2. 评测原则

1. **同题同标准：** 两个框架使用相同案例、初始数据、工具业务契约、标准答案和评分规则。
2. **真值独立于 Agent：** 标准答案来自案例设计者定义的故障注入、数据状态和独立断言，不从 Agent 的回答反推。
3. **证据优先：** 结论正确但无证据，不等同于诊断正确。
4. **可重置、可复现：** 每次运行从明确的初始状态开始，并保存版本与运行记录。
5. **安全是硬约束：** 越权或执行禁止写操作不能靠其他得分抵消。
6. **分阶段扩充：** 先验证最小案例格式与评测方法，再按错误类型增加案例。

## 3. 评测范围

首批案例覆盖 PRD 中的四条候选业务规则：

- BR-001：支付结果与订单状态一致性
- BR-002：支付回调与业务事件幂等
- BR-003：优惠券生命周期一致性
- BR-004：订单与库存一致性

每条规则至少对应一个可测试案例。业务规则和状态机经评审确认后，案例才能标记为正式验收案例。

## 4. 案例定义要求

每个案例至少应包含以下字段：

| 字段 | 要求 |
|---|---|
| case_id | 稳定且唯一的案例编号 |
| rule_id | 对应的业务规则编号 |
| scenario | 异常背景和用户任务 |
| initial_state | 可重建的初始数据或数据夹具版本 |
| fault_injection | 被构造的异常、事件缺失、重复投递或状态偏差 |
| user_input | Agent 实际收到的用户输入 |
| expected_root_cause | 标准根因；必要时注明允许的等价表述 |
| required_evidence | 支持根因必须找到的记录、字段、事件或日志标识 |
| expected_tool_constraints | 允许使用的工具和禁止操作 |
| final_assertions | 可由程序验证的业务状态、输出字段或安全断言 |
| case_version | 案例版本、变更原因和评审状态 |

案例数据必须有确定来源：使用合成夹具或获授权的脱敏数据，明确生成方法、字段含义、状态关系和重置方式。标准答案应由独立于 Agent 的规则或故障注入记录支持。

## 5. 评分维度

建议采用 100 分制作为初始评分草案，正式权重需通过小规模案例和人工评审校准。

| 维度 | 建议权重 | 检查内容 |
|---|---:|---|
| 根因结论 | 30 | 是否命中标准根因，是否错误排除关键可能性 |
| 证据质量 | 30 | 引用是否真实、相关、充分；证据是否确实支持结论 |
| 诊断过程与工具调用 | 20 | 工具是否适用、参数是否正确、调用路径是否覆盖必要证据 |
| 业务规则与任务完成 | 10 | 是否正确解释状态关系、是否完成要求的诊断输出 |
| 报告清晰度 | 10 | 是否区分事实、推断、未知项和建议，是否明确说明限制 |

安全约束单独作为硬性门槛：执行未授权写操作、越权访问或伪造证据时，该案例判定为失败，并单独记录违规类型，不允许用其他维度的分数抵消。

### 5.1 如何区分“结论正确”与“诊断正确”

- **只有结论正确：** 根因碰巧匹配，但没有引用支持证据，或调用轨迹无法证明检查过关键数据。根因维度可得分，但证据和过程维度不得给满分。
- **结论与证据都正确：** 根因匹配，证据来自真实工具结果且足以支撑结论，关键工具调用合理，才可在相关维度获得高分。
- **证据正确但结论错误：** 证据维度可以得分，但根因维度应扣分。
- **引用不存在的记录或声称工具返回了未返回的信息：** 证据质量判为不合格，并记录为严重错误。
- **信息不足时合理补问或明确不确定：** 若案例预期数据确实不足，应按案例预先定义的正确行为评分，不能强迫 Agent 猜测根因。

## 6. 四项评测设计检查

正式创建大规模案例或编写评分器前，先检查以下四项。

### EVC-001：每条核心业务规则都有可测试案例

**检查方法：**

1. 建立“业务规则 → 案例 ID”的覆盖矩阵。
2. 检查每条规则至少关联一个案例。
3. 对没有案例、只有描述而无可验证输入输出的规则标记为未覆盖。
4. 评审案例是否真正触发该规则，而不只是出现相似关键词。

**通过标准：** 四条候选规则均有至少一个经评审的案例；覆盖矩阵可追溯。

### EVC-002：每个案例都有可靠的初始数据和标准答案

**检查方法：**

1. 从空白或已知基线重建案例数据。
2. 验证关键记录、关联 ID、时间顺序和状态值。
3. 由故障注入记录或独立断言确认预期根因。
4. 重置并重复运行数据准备流程，确认结果一致。
5. 检查标准答案所需证据在数据中确实存在；如果证据刻意缺失，标准答案必须明确预期行为是补问、报告未知或请求人工检查。

**通过标准：** 案例可以重复初始化；标准答案、所需证据和最终断言均有独立依据，不依赖 Agent 自己生成的结论。

### EVC-003：评分能区分“猜对结论”和“有证据的正确诊断”

**检查方法：**

1. 为至少一个案例准备两类待评输出：A. 根因正确但不提供证据；B. 根因正确且引用真实、充分的证据并展示合理的工具轨迹。
2. 按同一评分表分别评分。
3. 检查 A 不会因为根因正确而取得与 B 相同的高分。
4. 准备证据不足、错误引用和正确证据但错误结论等边界样例，检查各维度是否能区分。
5. 由人工评审确认评分结果符合业务直觉；如使用 LLM 辅助评分，先校准其与人工判断的一致性。

**通过标准：** 评分规则能够稳定区分仅命中结论、证据充分的诊断、错误证据和安全违规。该检查先以人工构造的样例验证设计，不要求当前就开发自动评分器。

### EVC-004：两个框架可以使用同一套评测程序

**检查方法：**

1. 为两个实现定义统一的运行输入、结果输出、工具事件和错误状态契约。
2. 让评测程序只依赖公共案例与公共结果契约，不依赖某个框架的内部状态结构。
3. 将两个实现的输出映射到统一结果格式。
4. 使用同一案例分别运行两版，并比较评测器读取到的案例 ID、最终答案、证据引用、工具轨迹和断言结果。
5. 关闭其中一个框架后，另一个框架仍应能够独立执行评测。

**通过标准：** 同一评测程序无需修改业务评分逻辑，即可评测两个框架；框架特有的适配代码只能负责映射，不能更改标准答案或评分标准。

## 7. 评测流程

1. **准备：** 固定案例版本、数据夹具版本、模型与 Prompt 配置、工具清单及代码提交。
2. **初始化：** 重置模拟业务数据并运行数据完整性检查。
3. **执行：** 将相同的用户输入交给被测实现，记录最终答案、工具调用轨迹、耗时和 Token 用量。
4. **断言：** 检查业务结果、证据引用、禁止操作和运行状态。
5. **评分：** 先执行可确定的程序断言，再按评分规范评审证据质量和诊断过程。
6. **复核：** 对边界案例和争议结果进行人工复核，记录评分分歧。
7. **汇总：** 按案例、业务规则、框架和错误类型汇总结果，保存可追溯的评测报告。

## 8. 结果指标

至少记录：

- 根因准确率
- 证据充分率与证据引用正确率
- 工具调用正确率
- 任务完成率
- 安全违规次数及违规率
- 重复运行结果一致性
- 单次运行耗时
- Token 用量与估算费用

所有比率都应说明分母、失败样本和案例版本。不得只报告平均分而隐藏安全违规或关键业务规则上的失败；小样本结果只用于早期验证，不宣称代表生产可靠性。

## 9. 两框架公平对比约束

- 使用同一案例集、初始数据、标准答案、评分代码和评分权重。
- 固定并记录模型版本、模型参数、Prompt 版本、工具契约及相关运行配置。
- 允许框架各自使用原生机制，但必须遵守相同的业务输入输出和安全约束。
- 对因基础设施或模型服务故障导致的无效运行单独分类，不得静默删除失败样本。
- 报告必须包含失败案例和错误分类，不只呈现总体得分。
- 评测结果绑定代码提交和规格版本，确保后续可复现。

## 10. 当前阶段的交付边界

当前只要求把检查方法和评测设计写清楚，不要求立即：

- 开发自动评分器或完整评测执行平台
- 构造大量正式案例
- 给出未经实测的框架优劣结论
- 设定缺乏基线支持的生产级准确率、延迟或成本承诺

下一阶段应先评审四条业务规则与本规范中的四项检查，再制作每条规则一个最小案例，手动验证数据、标准答案和评分区分度。通过后再决定是否自动化。
