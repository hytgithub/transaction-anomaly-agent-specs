# 产品需求文档（PRD）

- 项目：交易业务异常诊断 Agent
- 文档版本：0.1.0-draft
- 状态：草案，待需求验收
- 最近更新：2026-10-22

## 1. 项目目标

构建一个面向交易业务研发与技术支持人员的智能体。用户用自然语言描述交易异常，Agent 在授权的模拟环境中查询订单、支付、优惠券、库存和事件记录，收集可追溯证据，判断可能的根因，并输出诊断结论、证据、尚未确认的假设及建议的下一步检查。

项目同时实现 AgentScope 与 LangGraph 两个版本，用同一套业务需求、测试数据和评测规范进行验证。目标是通过可复现的测试结果比较两种框架的实现与运行表现，而不是凭演示效果主观判断。

## 2. 目标用户与典型问题

### 2.1 目标用户

- 交易业务研发人员
- 负责线上问题初步分析的技术支持人员
- 需要核对业务状态、事件流和处理记录的测试人员

### 2.2 首批问题范围

1. 支付已成功，但订单状态未更新。
2. 支付回调或业务消息重复到达，可能造成重复处理。
3. 优惠券状态与订单状态不一致。
4. 订单状态与库存扣减、释放结果不一致。

以上是首批训练场景，不代表系统已经具备诊断能力。每类场景都必须用可重置的模拟数据和明确的标准答案验证。

## 3. 用户价值与成功标准

Agent 应帮助用户更快定位交易异常，并降低无证据猜测和不安全操作的风险。项目初期不预设节省比例或准确率目标；先建立可靠的基线，再根据评测结果确定目标。

需要观察的核心指标：

- 根因判断是否正确
- 证据是否真实、相关、充分且可追溯
- 工具选择与调用是否正确
- 是否违反权限或操作边界
- 任务完成率与重复运行稳定性
- 响应耗时、Token 用量及模型调用成本

## 4. 核心业务规则（待业务评审确认）

### BR-001：支付结果与订单状态一致性

支付结果、支付流水和订单状态应满足定义明确的状态转换关系。支付渠道显示成功但订单仍处于待支付状态时，Agent 应核对支付记录、回调接收记录、消息消费结果及订单状态变更记录，不能仅凭最终状态猜测根因。

### BR-002：支付回调与业务事件幂等

同一业务事件重复投递或重试，不应导致重复支付入账、重复状态迁移或重复业务副作用。诊断时应核对事件标识、业务流水号、消费记录和状态变更历史。

### BR-003：优惠券生命周期一致性

优惠券的可用、锁定、核销、释放或失效状态，应与订单创建、支付、取消等业务状态及既定规则保持一致。Agent 应通过优惠券记录和订单事件判断异常所在，不得把“状态不同”直接等同于“数据错误”，还需考虑业务定义允许的中间态。

### BR-004：订单与库存一致性

库存扣减、释放与订单创建、支付、取消等状态变化，应符合明确的库存业务规则。诊断需检查库存流水、订单事件和相关处理结果；不得仅根据库存当前值推断具体根因，也不得建议未经证据支持的直接改库操作。

> 说明：以上规则是首版候选规则。实现前需明确状态机、允许的中间态、时间窗口、事件关联键及异常判定条件，并为每条规则建立标准案例。若业务方规则与本文不同，应通过变更记录修订本文，而不是让两个框架各自解释。

## 5. 核心用户流程

1. 用户描述异常，提供已知的订单号、支付流水号或时间范围。
2. Agent 判断现有信息是否足以查询；必要时提出有针对性的补充问题。
3. Agent 通过只读工具查询相关业务状态、流水、事件与处理日志。
4. Agent 将观察到的事实与推测分开，并检查证据是否支持候选根因。
5. Agent 输出诊断结果，包括：
   - 异常摘要与影响对象
   - 最可能根因及置信说明
   - 支持结论的证据和来源标识
   - 尚未确认的信息及下一步检查建议
   - 是否需要人工处理
6. 测试程序检查结构化结果、证据引用、工具轨迹和最终业务断言。

## 6. 功能需求

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-001 | 理解用户的异常描述 | 能识别问题类型和已提供的业务标识；信息不足时能补问 |
| FR-002 | 查询模拟交易数据 | 通过受控只读工具查询订单、支付、优惠券、库存和事件记录 |
| FR-003 | 形成证据链 | 每条关键事实可追溯到工具返回的记录、字段或事件标识 |
| FR-004 | 给出根因诊断 | 根因结论与标准答案对照；证据不足时明确说明不确定性 |
| FR-005 | 生成可验证的诊断报告 | 区分事实、推断、未知项和建议，不编造不存在的记录 |
| FR-006 | 记录运行轨迹 | 可获取工具调用、关键输入输出、最终答案、耗时和 Token 用量 |
| FR-007 | 支持重复评测 | 案例数据可重置；相同输入可重复运行并比较结果 |
| FR-008 | 支持双框架一致验收 | 两个实现遵守同一业务输入输出契约，并接入同一评测程序 |

## 7. 安全与操作边界

首阶段采用只读模拟环境：

- 不连接真实生产交易系统。
- 不执行真实退款、核销、库存修改、订单修复或其他写操作。
- 不把模型生成的猜测作为事实。
- 不伪造日志、流水、工具返回值或证据引用。
- 工具访问范围由应用侧权限和参数校验控制，不能仅依赖 Prompt。
- 所有案例使用合成或经过授权、脱敏的数据。

后续若考虑修复操作，必须另行定义授权、人工确认、幂等、审计、回滚与最终状态核验要求，并经单独评审。

## 8. 首阶段范围与非目标

### 本阶段包含

- 需求和核心业务规则梳理
- 可重置的模拟交易数据设计
- 评测案例格式与标准答案定义
- 统一的评测方法和评分规则设计
- AgentScope 与 LangGraph 的可比性约束

### 本阶段暂不包含

- 生产系统或真实支付渠道接入
- 自动修复交易数据或执行补偿操作
- 立即开发完整评分器
- 一次性创建大量测试案例
- 未经验证的准确率、成本节省或生产可靠性承诺

## 9. 验收标准

PRD 进入实现阶段前，应至少确认：

1. 四条核心业务规则的状态条件、异常条件和允许的中间态已由业务评审确认。
2. 每条规则至少有一个可重置、可独立执行的候选案例。
3. 每个案例的输入、初始数据、预期根因、证据要求和最终断言定义明确。
4. 只读工具范围与禁止操作明确。
5. AgentScope 与 LangGraph 的共用契约边界明确。
