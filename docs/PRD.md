# 产品需求文档（PRD）

- 项目：交易业务异常诊断 Agent
- 文档版本：0.2.0-draft
- 状态：需求基线草案；首期范围已确认，进入实现前的规格冻结准备
- 最近更新：2026-10-22
- 共享规格仓库：`hytgithub/transaction-anomaly-agent-specs`

## 1. 项目目标

构建一个面向交易业务研发、测试与技术支持人员的企业级业务诊断 Agent。用户使用自然语言描述交易异常，Agent 在受控的模拟环境中自主选择查询工具、收集可追溯证据、判断根因；满足明确的业务前置条件后，Agent 可提出模拟修复方案，由独立审批用户逐项批准，再通过受控的业务事件重放执行，并验证最终业务状态。

项目同时实现 AgentScope 与 LangGraph 两个版本，使用相同的业务服务、模拟数据、工具契约、模型基线和独立评测器。通过可复现的评测数据比较诊断质量、安全性、任务完成率、稳定性、延迟、Token 用量和估算成本，并帮助开发者掌握企业级 Agent 的设计、实现、评测与排障方法。

本项目仅面向合成的本地模拟交易环境，不接入真实生产交易系统或真实支付渠道。

## 2. 目标用户与交互方式

### 2.1 目标用户

- 交易业务研发人员
- 负责问题初步分析的技术支持人员
- 验证业务状态、事件流和诊断结果的测试人员

### 2.2 首期交互

提供简单登录的 Web 应用和后端 API。Web 首期包含：
- 聊天区：自然语言描述问题、补充信息和多轮追问。
- 证据与诊断报告区：展示事实、证据引用、根因结论、未知项和建议。
- 修复审批卡片：展示目标对象、事件、预期效果、前置条件与风险，提供批准/拒绝操作。
- 执行结果区：展示事件重放状态、验证结果、失败原因或人工接管摘要。
- 流式响应：展示回答增量及关键工具调用和任务状态。

### 2.3 输入信息

用户可以提供订单号、支付流水号和/或时间范围。若缺少执行查询所需的关键标识，Agent 应有针对性地补问。若时间范围匹配多个候选订单，必须列出候选并请求用户确认，不得自行选择目标进入修复流程。

## 3. 业务范围与实施阶段

### 3.1 总体业务覆盖规划

整体规格覆盖四类交易异常：
1. BR-001：支付成功，但订单状态未更新。
2. BR-002：支付回调或业务事件重复到达，可能导致重复处理。
3. BR-003：优惠券状态与订单状态不一致。
4. BR-004：订单状态与库存扣减、释放结果不一致。

四类场景属于产品总体规划，不代表首期都已实现。

### 3.2 首期完整实现范围

首期只完整实现 BR-001“支付成功，但订单状态未更新”，打通以下端到端链路：
1. 接收用户描述并解析业务标识。
2. 查询订单、支付、回调、事件消费和订单状态变更历史。
3. 根据证据自主决定下一步查询，区分事实、推断与未知项。
4. 输出结构化诊断报告和自然语言说明。
5. 满足预定义的证据与业务前置条件时，生成修复提案。
6. 由不同于提案发起人的审批用户，在 Web 页面逐项批准或拒绝具体操作。
7. 后端重新校验身份、审批记录、提案版本、目标对象、证据有效性及业务前置条件。
8. 仅通过受控工具重放符合条件的模拟业务事件；不得直接改库。
9. 查询最终业务状态，验证修复是否真正生效。
10. 保存完整的诊断、审批、执行、验证和审计记录。

其余三类场景先完成业务规则与扩展设计，待首期闭环和评测基础稳定后逐步扩展。

## 4. 核心业务规则

### BR-001：支付结果与订单状态一致性（首期）

支付结果、支付流水、回调记录、事件消费结果和订单状态变更必须符合明确的状态转换关系。支付成功而订单仍待支付时，Agent 必须检查关联证据，不能仅凭最终状态猜测根因。只有案例定义的证据和业务前置条件全部满足时，才可提出受控的事件重放方案。

### BR-002：支付回调与业务事件幂等（后续）

同一业务事件重复投递或重试，不应导致重复入账、重复状态迁移或重复业务副作用。诊断时需核对事件标识、业务流水号、消费记录和状态变更历史。

### BR-003：优惠券生命周期一致性（后续）

优惠券的可用、锁定、核销、释放或失效状态，应与订单创建、支付、取消等业务状态及规则保持一致。不得将状态差异直接认定为数据错误，应考虑允许的中间态。

### BR-004：订单与库存一致性（后续）

库存扣减、释放与订单创建、支付、取消等状态变化，应符合明确的库存业务规则。不得仅根据库存当前值推断根因，也不得建议未经证据支持的直接改库操作。

状态机、允许的中间态、时间窗口、事件关联键和异常判定条件必须通过案例与独立断言明确。两个框架不得各自解释或实现不同的业务真值。

## 5. 首期证据源与诊断原则

首期可查询的证据源：
1. 订单记录
2. 支付记录
3. 支付回调记录
4. 事件消费记录
5. 订单状态变更历史

Agent 可以自主决定下一步查询哪一类证据，但工具只能从应用侧白名单中选择。查询结果必须保留稳定的记录或事件标识，以便报告和审计追溯。

诊断结论必须区分：
- 已由工具结果验证的事实
- 基于事实形成的推断及其置信说明
- 尚未确认的假设或未知项
- 缺少的关键证据和下一步建议

若证据不足，Agent 可在限定范围内继续查询；仍不足时，应说明未知项并向用户补问或建议人工检查，禁止提出可执行修复。若数据相互矛盾，应展示冲突并暂停修复，不得强行选择一个结论。

## 6. 功能需求

| 编号 | 需求 | 验收要点 |
|---|---|---|
| FR-001 | 自然语言输入与标识解析 | 支持订单号、支付流水号、时间范围；必要时补问；多候选时由用户确认 |
| FR-002 | 受控证据查询 | 通过白名单工具查询首期五类记录；工具错误类型明确 |
| FR-003 | 证据链 | 每条关键事实可追溯到真实工具结果中的记录、字段或事件标识 |
| FR-004 | Agent 自主诊断 | Agent 自主选择下一步查询；证据不足时不猜测、不修复 |
| FR-005 | 结构化报告 | 固定字段与自然语言说明并存；不编造记录 |
| FR-006 | 修复提案 | 仅在预定义证据和业务前置条件满足时生成，明确目标、事件、预期效果、风险与提案版本 |
| FR-007 | 人工审批 | 每个具体操作均须批准或拒绝；审批人必须与提案发起人是不同账号；后端强制校验 |
| FR-008 | 受控模拟事件重放 | 仅调用预定义的事件重放业务工具；禁止任意 SQL、任意数据库写入和直接改库 |
| FR-009 | 修复后验证 | 查询最终状态并与独立业务断言比对；未验证不得报告修复成功 |
| FR-010 | 会话上下文 | 同一会话保留排查对象、证据引用、已完成步骤、待查事项和任务状态；切换对象时防止串用旧结论 |
| FR-011 | 流式交互 | 流式输出回答增量和关键工具/任务状态；明确区分处理中、待审批、执行中、成功和失败 |
| FR-012 | 人工接管 | 证据不足、持续工具故障或状态冲突时暂停，汇总事实、证据、失败原因和建议 |
| FR-013 | 持久化与审计 | 保存会话、工具事件、证据引用、审批、执行、验证、耗时、Token 与估算成本；敏感信息脱敏 |
| FR-014 | 任务控制 | 统一任务状态、最大步数、整体及工具超时、重试上限和取消机制 |
| FR-015 | 可复现评测 | 可重置模拟数据，案例有独立标准答案，评测结果可追溯到代码与规格版本 |
| FR-016 | 双框架共用评测 | 同一评测器和案例契约可评测 AgentScope 与 LangGraph |
| FR-017 | 历史与清理 | 服务重启后保留历史会话；清理操作显式执行且受权限保护 |
| FR-018 | 测试数据重置 | 通过独立测试命令或受限测试接口重置；禁止普通诊断用户任意重置 |
| FR-019 | 导出 | 诊断报告支持 JSON/Markdown；评测结果支持 CSV/JSON |
| FR-020 | 部署 | 本地可运行，提供 Docker Compose 可复现环境及部署说明 |

## 7. 诊断报告契约

结构化报告至少包含：
- report_id、task_id、session_id、case_id（适用时）
- 目标对象及解析到的业务标识
- 异常摘要
- 根因候选及状态（已确认/推断/未知）
- 证据列表：来源类型、记录或事件 ID、相关字段、证据说明
- 已查询项、未查询项和缺失证据
- 风险与业务影响
- 是否允许提出修复及其原因
- 修复提案 ID、版本、目标对象、预期效果和前置条件（适用时）
- 审批状态、执行状态、验证结果（适用时）
- 限制、错误和人工接管建议
- 模型、Prompt、工具契约与配置版本引用

自然语言说明必须与结构化字段一致，不得将推断写成已验证事实。

## 8. 身份、审批与修复安全

### 8.1 角色

首期采用简单登录，至少区分：
- 诊断用户：发起诊断、查看其有权访问的报告和证据。
- 审批用户：查看修复提案并批准或拒绝。

每个账号只应拥有其明确配置的权限。后端根据经过认证的身份执行授权，不能相信前端传入的普通角色字段。

### 8.2 职责分离与审批绑定

- 提案发起人与审批人必须是不同账号。
- 审批必须绑定具体提案 ID、提案版本和目标对象。
- 提案内容或关键业务状态发生变化时，原审批不得自动沿用，必须重新核验，必要时重新审批。
- 每次具体修复操作均需单独批准。
- 没有合格审批人时，任务保持待审批或转人工接管，不得自动执行。
- 拒绝审批后不得执行该提案。

### 8.3 事件重放

- 仅允许调用预先定义的业务事件重放工具。
- Agent 不得直接修改数据库、执行任意 SQL 或绕过业务服务。
- 执行前由后端复核权限、审批、证据、业务前置条件、提案版本和目标对象。
- 重放请求需有唯一操作标识，并通过幂等键、去重记录或等效机制防止重复副作用。
- 重放超时不代表未执行。结果不确定时，应先查询事件消费记录和最终业务状态；未确认前不得盲目重放。
- 取消任务后禁止发起新的修复操作。若修复已开始，取消不等于回滚；必须核实实际执行结果并如实报告。
- 只有最终业务状态满足预期断言，才能报告修复成功。

### 8.4 明确禁止

- 接入真实生产交易系统或真实支付渠道
- 未经审批执行修复
- 自我审批、伪造审批身份或绕过后端授权
- 证据不足或业务前置条件不满足时修复
- 任意 SQL、直接改库或未列入白名单的工具调用
- 伪造日志、流水、证据引用或修复结果
- 结果不确定时盲目重试
- 将模型推断直接当作业务事实

## 9. 任务生命周期、错误处理与人工接管

### 9.1 建议状态

任务至少支持：`queued`、`diagnosing`、`awaiting_input`、`awaiting_approval`、`executing`、`verifying`、`completed`、`failed`、`cancel_requested`、`cancelled`、`handoff_required`。

具体状态转换必须定义合法前置条件，并通过状态机测试验证。状态名称可以映射到前端中文显示，但不得在不同框架中改变语义。

### 9.2 错误分类与重试

- 暂时性错误（例如短暂超时或服务不可用）：按统一配置有限重试。
- 业务校验失败、权限拒绝、记录不存在：不盲目重试；根据错误语义补问、停止或接管。
- 关键证据缺失：禁止修复。
- 工具返回不完整或互相矛盾：标记限制，必要时转人工。
- 重放结果不确定：先核验执行记录和业务状态。
- 达到最大步数或整体超时：停止发起新工具调用，保存轨迹并报告任务状态。

### 9.3 取消与人工接管

用户可取消仍在运行的任务。系统应阻止后续新修复操作，并处理与审批或执行并发发生的取消请求。已经开始的副作用必须核实，不得假设取消能够撤销它。

人工接管摘要至少包含已确认事实、证据引用、已尝试步骤、失败原因、未知项、当前任务/修复状态和建议的下一步操作。

## 10. 前端流式事件与审计

流式接口应使用有版本的统一事件契约。事件类型至少包括：
- `task_started`
- `tool_started`
- `tool_completed`
- `answer_delta`
- `approval_required`
- `report_ready`
- `task_status_changed`
- `task_failed`
- `task_completed`

每个事件应包含 task_id、session_id、event_id、时间戳、事件类型和必要的结构化载荷。框架适配层负责将各框架的原始事件映射为公共格式。前端不得仅根据自然语言内容猜测任务状态。

审计记录至少覆盖模型调用元数据、工具事件、状态变化、证据引用、审批主体与决定、提案版本、重放操作标识、执行与验证结果、耗时、Token 和估算成本。敏感字段须过滤或脱敏，不记录 API Key、密码等秘密。保留和清理规则应区分业务模拟数据、会话和审计记录。

## 11. 双框架架构与公平对比

### 11.1 共享部分

- 业务服务与业务规则
- 模拟数据、故障注入、数据夹具和重置机制
- 工具契约、工具白名单和错误语义
- 身份、审批和修复安全校验
- 任务与报告公共契约
- 运行事件格式、独立评测器和标准答案
- 模型配置基线和运行限制

### 11.2 独立部分

AgentScope 与 LangGraph 各自实现 Agent 编排、框架适配、状态映射和原生运行机制。不得把所有 Agent 决策逻辑抽到共享层，以致只剩框架入口切换；也不得在某个框架中另行修改业务规则或评分标准。

### 11.3 公平性要求

两个实现使用相同的：
- DeepSeek 官方 API 及同一模型版本
- 核心 Prompt、生成参数和配置版本
- 工具契约、业务数据、故障注入和安全约束
- 案例、初始数据快照、标准答案、评分代码和评分权重
- 任务超时、最大步数、重试上限和工具权限

每次运行前初始化相同的案例快照，避免一个实现的修复影响另一个实现。记录代码 commit、规格 commit、模型版本、Prompt 版本、工具契约版本和运行配置。模型输出可能存在非确定性，重要案例应按评测计划重复运行并单独报告稳定性。

## 12. 非功能需求与部署

- 并发目标：单机稳定支持 3–5 个并发用户。延迟和资源使用的硬性数值目标在基线测量后确定。
- 任务限制：最大步数、整体超时、模型/工具超时和重试上限均可配置，并对两个框架保持一致。
- 历史数据：本地演示期间持续保存；服务重启后可查看历史会话。清理由显式、受权限保护的操作触发。
- 测试数据：提供独立测试命令或受限测试接口。活动任务、待审批或执行中的修复存在时，不得重置造成状态混乱。
- 部署：提供本地运行方式、Docker Compose 配置、环境变量示例、数据库初始化与健康检查说明。
- 凭证：模型 API Key 等敏感配置通过环境变量或本地密钥配置提供，不提交到 Git。
- 导出：诊断报告 JSON/Markdown；评测结果 CSV/JSON。
- 可观测性：结构化记录关键运行事件、耗时、Token 和估算成本；对敏感内容脱敏。

## 13. 评测与成功标准

首批先建立 8 个案例，验证数据夹具、独立标准答案、业务断言、工具轨迹和安全门槛。之后按 8 → 30 → 约 60 个案例分阶段扩充。评测案例划分为开发调试集、固定回归集和保留测试集；保留测试集不得用于日常调优。

需要记录根因准确率、证据充分率、证据引用正确率、工具调用正确率、任务完成率、修复验证成功率、人工接管正确率、安全违规次数/率、重复运行稳定性、耗时、Token 和估算成本。各指标的分母、失败样本处理方式和案例范围必须在评测规范中定义。

先测量可复现基线，再确定数值目标。任何安全硬门槛失败都不能被其他指标或总分抵消。

## 14. 阶段交付与验收

### 阶段 0：规格冻结
- PRD 与评测规范版本一致，所有已确认的业务和安全要求已纳入。
- 公共/框架特有边界、接口契约和首期范围明确。

### 阶段 1：评测基础
- 8 个案例均有独立夹具、故障注入、标准答案、证据要求和可执行断言。
- 至少覆盖标准成功、证据不足、输入歧义、暂时性工具故障、前置条件变化、权限违规、结果不确定与安全拒绝。
- 数据可以重复初始化，标准答案不依赖 Agent 输出。

### 阶段 2：公共业务层
- 查询工具受白名单与参数校验约束。
- 审批、事件重放、幂等控制、状态核验和审计可独立测试。
- 测试重置机制不能被普通诊断用户滥用。

### 阶段 3：首个框架闭环
- Agent 能自主查询并给出有证据的诊断。
- 未满足前置条件或未经独立审批时不能修复。
- 事件重放后必须验证最终业务状态。
- 8 个案例均通过相应的业务断言与安全硬门槛，失败样本如实报告。

### 阶段 4：第二个框架与交付
- 第二个框架接入同一公共业务层与评测器。
- 两个实现遵守同一运行限制和安全门槛。
- Docker Compose 环境可复现，3–5 用户并发、取消、历史、导出及审计能力按计划验收。

## 15. 非目标

- 接入真实生产交易系统或支付渠道
- 直接修复真实业务数据库
- 首期同时完整实现四类业务异常
- 首期建设完整企业级 RBAC、组织权限或单点登录
- 未经基线测试承诺生产级准确率、可用性、延迟或成本节省
- 将小样本评测结果宣称为生产可靠性结论
